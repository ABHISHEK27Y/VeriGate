\section{Boundary, Notation, and Source Checkpoint}
The diagrams in this chapter describe the implemented gateway as inspected at source commit \texttt{1cdb80a78ebb8bd00a53cea42aa080a523af950e}. They abstract selected paths rather than asserting that every script in the repository was audited. Concurrent application changes after this checkpoint need reconciliation before the drawings are used as a release record. The client is an integrated application acting for an authorized principal; the gateway does not intercept an ordinary ChatGPT or Codex session. Gateway credentials identify the caller, while server-configured provider profiles supply any upstream secret.

Figures~\ref{fig:dfd_context_full} and \ref{fig:dfd_level1_full} use the Yourdon/DeMarco data-flow convention: circles are numbered transformations, rounded rectangles are external entities, open-ended parallel lines are logical data stores, and labelled one-way arrows carry data. A DFD explains what crosses a boundary, not the order of conditionals. The flowcharts (Figures~\ref{fig:request_flow_full} and \ref{fig:candidate_decision_full}) use terminators, process rectangles, decision diamonds, and labelled yes/no branches, and the deployment drawing (Figure~\ref{fig:deployment_full}) uses container boundaries and communication links. These notations answer different questions and are not interchangeable. Shape carries the notation and colour reinforces the outcome: blue for a process, amber diamonds for a decision, teal for an interaction or alternate path, green for a successful terminator, red for an error or deny exit, and slate for an external entity or store. Shape and text retain their meaning in grayscale; colour is only a reading aid.

\section{Actors and Supported Goals}
Two actor roles drive the gateway directly. A client requests a technical answer and receives the outcome as part of that request; receiving an HTTP response is not a separate business use case. An operator can inspect occupancy or health/metrics data and can clear the caller's own private cache through supported routes. The cache-clear route does not erase an authorized workspace's shared answers for a normal user. The metric route uses its token dependency; the administration routes require the gateway credential. Some operational endpoints are also useful to automated deployment probes rather than a human operator.

\section{Context Data Flow}
Figure~\ref{fig:dfd_context_full} has exactly one process, ``0---VeriGate LLM Gateway.'' The client sends a gateway credential and prompt and receives an answer with outcome metadata or an error. In an external-provider configuration, the gateway sends a generation request and receives provider events, usage, or an error. The local mock profile stays inside the gateway boundary and therefore does not use the external arrow. Redis and local MiniLM/NLI inference are internal implementation components at this context level.

The operator flow represents concrete routes: \texttt{/admin/cache/clear}, \texttt{/admin/cache/occupancy}, \texttt{/admin/config}, \texttt{/metrics}, \texttt{/health}, \texttt{/ready}, and \texttt{/live}, each with its implemented access rule. An administrator does not push runtime configuration into the gateway through a depicted management API. Settings, provider secrets, and the optional organization directory are deployment inputs, discussed in Figure~\ref{fig:deployment_full}.

\section{Level-1 Data Flow and Stores}
Figure~\ref{fig:dfd_level1_full} expands process 0 into eight logical transformations. Process 1.0 checks the request and gateway credential using D1's credential data. Process 2.0 resolves the authorized principal, compatible provider profile, workspace/private scope, and request eligibility using the same directory. Process 3.0 asks D2 for scoped exact or vector candidates and receives current candidate records. Process 4.0 assesses whether a stored answer fits the incoming task, returning a selected cached answer or a reason to generate. Process 5.0 applies admitted-miss control and obtains configured provider events. Process 6.0 validates the completed answer, classifies storage eligibility, and writes an eligible record to D2. Process 7.0 assembles content and outcome metadata. Process 8.0 represents the operational routes so operator data does not enter a client-response process by implication.

D1 is configuration loaded into the process, D2 is the scoped cache and optional RedisSearch vector index, D3 holds admitted-miss and quota state, and D4 is local policy/model material. D2 and D3 are logical stores that share Redis in the Redis-backed profile; they are not separate database servers. D4 is per worker. An arrow carrying a candidate list is data, while a cache HIT or MISS is a later request outcome. The diagram abstracts the private overlay, index overfetch, failure exits, and atomic Redis transactions; the flowcharts and text below locate those details.

\section{JSON Request Control Flow}
Figure~\ref{fig:request_flow_full} describes the JSON handler's admission and lookup path. Request middleware limits body size and concurrency; schema validation and gateway authentication must succeed before cache work. The handler resolves a principal and registry, checks the rate limit, builds the prompt, and resolves an authorized scope. A no-store or explicit bypass request goes directly to generation. For a workspace request the private overlay is checked first; the scoped exact key is checked before any embedding. If semantic mode is active and exact lookup misses, MiniLM embeds the question and the selected backend retrieves a scope-filtered top-$k$ set. An empty shortlist, VERIFY, REJECT, conflict, verification limit, deadline, changed entry, or unavailable cache produces a MISS reason rather than a cached answer.

The candidate decision in Figure~\ref{fig:candidate_decision_full} is a subprocess of this lookup, not an extra request path. A selected semantic entry is re-read before a HIT and its recency is touched without extending the entry's TTL. The gateway then rechecks the principal before publishing the HIT. A credential change returns an authorization error. The B connector leads to generation, described in the next section: both BYPASS and an unsuccessful lookup require admitted-miss control before a provider call.

\section{Generation, Completion, and Storage Control}
The gateway checks the principal again and counts one admitted miss or bypass. A rate rejection, unavailable admission state, or expired request deadline exits before a provider call. For a JSON MISS, a process-local singleflight key can let a concurrent follower receive the leader's completed answer; BYPASS generates directly. The provider registry selects an explicitly configured route and may use a configured alternate after a circuit-breaker or provider failure. It never silently substitutes the development mock for a real-provider failure.

The JSON generation function assembles content events and requires one normal terminal completion, a nonempty answer, and the configured response length bound. A timeout, incomplete stream, duplicate completion, or other provider error becomes an explicit error with no cache write. On success, the response classifier can mark the answer no-store, privately eligible, or shareable. A fallback route is not written under the intended route's identity. An eligible workspace response may be downgraded to the caller's private scope. A cache write may succeed, be refused by limits, time out, or fail; a completed answer is still returned with the recorded storage outcome, so a provider MISS and a non-success storage result remain distinct in the metadata. Streaming follows its own event/cancellation state machine and has no JSON singleflight guarantee.
