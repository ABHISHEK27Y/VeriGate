\section{Introduction}
This chapter separates three kinds of evidence: (i) the semantic-cache policy benchmark, (ii) component latency and routing experiments, and (iii) software validation and operational checks. These are not interchangeable. In particular, the benchmark evaluates the configurable semantic policy; the deployed gateway currently defaults to exact-prompt cache matching, with semantic matching explicitly opt-in. Therefore, the semantic benchmark must not be presented as the default production request path.

\section{Semantic Cache Policy Evaluation}
\subsection{Benchmark Design}
The checked-in benchmark is a small, hand-curated test set containing 15 positive (equivalent) query pairs and 15 negative (non-equivalent) pairs. The negative set is divided into entity swaps (5), number swaps (3), negation changes (2), and related-topic pairs (5). A separate volatility check contains 5 time-sensitive queries and 4 stable controls. This dataset is useful for controlled mechanism-level comparison, but it is not a representative production query corpus.

The evaluation runner uses the same \texttt{CachePolicy} implementation as the semantic-cache component. It compares a fixed-threshold baseline ($T=0.72$), adaptive thresholding alone, Tier-1 structural verification alone, the combined adaptive-plus-Tier-1 policy, and the optional Tier-2 NLI configuration. The runner evaluates query pairs directly; it does not exercise the gateway's default exact-prompt mode or prove production-scale behaviour.

The result should be reported as \emph{zero observed false hits among 15 curated negatives}, rather than a universal guarantee.

\subsection{Volatility Check}
The keyword-based volatility detector flagged all 5 queries in the curated volatile set and none of the 4 stable controls. These results are counts on a small hand-selected set (5/5 detected; 0/4 stable controls flagged). The detector is a rule-based keyword matcher, not a trained classifier, so unlisted time-sensitive formulations can be missed and some unseen stable queries may be flagged.

\section{Tier-2 NLI Experiment}
The optional Tier-2 verifier uses a cross-encoder NLI model and checks entailment in both directions. In the checked-in policy results it accepts 3 of 15 positive pairs and 0 of 15 negative pairs (20.0\% hit rate, 0.0\% observed false-hit rate, 100.0\% precision). This is more conservative than Tier-1 alone and reduces reuse on the tested positives. NLI is disabled by default. It is a statistical model-based filter, not a formal proof of equivalence or a guarantee of correctness.

\section{Cost-Aware Cascade Experiment}
The cascade evaluator contains 20 hand-labelled easy queries and 20 hand-labelled hard queries. It uses a heuristic complexity score and an illustrative cost model in which the strong model is assigned 15 times the cost of the cheap model. At the configured threshold of 0.35, the checked-in \texttt{cascade.csv} reports a 50\% escalation rate, 46.7\% model-cost reduction versus always using the strong tier, 100\% retention of labelled hard queries on the strong tier, and an F1 score of 1.00. Random routing at the same escalation rate retains 50\% of hard queries.

These are results from a small labelled routing exercise and a simulated relative-cost model. They are not measurements of actual provider invoices, token usage, or answer quality from live model outputs. The routing implementation is a transparent heuristic based on query length and lexical/code/math cues; it is not a trained classifier. The cascade is optional and disabled by default.

\section{Security and Operational Behaviour}
The application derives an opaque tenant identifier from each API key using a salted HMAC-SHA256 digest. Cache records and semantic vector searches are tenant-scoped. The repository contains regression tests for tenant isolation and cross-worker state invalidation. The live RediSearch path still requires the release-gate integration run described above.

The daily budget is a per-key, per-UTC-day counter of admitted cache misses and bypasses. It is not a monetary spend cap: provider retries, cascade attempts, tokens, and actual provider charges are not measured by this counter. Monetary limits must be configured with the upstream provider. Rate limiting is implemented as a Redis token bucket, using a Lua script on real Redis and a WATCH-transaction fallback where scripting is unavailable.

The \texttt{/metrics} endpoint requires a bearer token or the supported metrics-token header. The application exposes separate \texttt{/live} and \texttt{/ready} health endpoints; readiness checks Redis and validates the RediSearch schema when semantic RediSearch mode is enabled. Provider health is reported as configuration-only, avoiding billable synthetic calls. Production startup validates non-demo credentials, a real provider, a private metrics token, a sufficiently long API-key salt, explicit CORS origins, shared Redis, and finite Redis memory configuration.

\section{Runtime Default and Interpretation}
A key implementation change is that \texttt{CACHE\_MATCH\_MODE} defaults to \texttt{exact}. Exact mode uses an authoritative Redis key derived from the exact UTF-8 prompt and its namespace; it does not run the approximate semantic candidate-selection path. Setting \texttt{CACHE\_MATCH\_MODE=semantic} opts into MiniLM embeddings, nearest-neighbour lookup, adaptive thresholding, and verification. The benchmark tables in this chapter evaluate that semantic policy and must be interpreted accordingly.

\section{Summary}
The repository contains a configurable LLM gateway with exact-prompt caching as its safe default and an opt-in semantic cache research path. On the small curated semantic benchmark, adaptive thresholding plus Tier-1 verification records zero accepted negative pairs out of 15, while retaining 5 of 15 positive pairs. The cascade's small labelled experiment reports 46.7\% simulated cost reduction at 100\% hard-query retention under a 15:1 assumed model-cost ratio. Local latency results show a sub-millisecond in-process KNN lookup at 1,000 entries, while embedding and optional NLI inference dominate the measured path. The test/audit record is encouraging but still requires fresh release-revision CI and live Redis Stack validation.
