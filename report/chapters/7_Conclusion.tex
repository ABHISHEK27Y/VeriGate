\section{Conclusion}
This project implements \textbf{VeriGate}, an asynchronous FastAPI gateway for LLM requests. It combines API-key authentication, tenant derivation, request limits, token-bucket rate limiting, cache management, provider routing and streaming, circuit-breaker state, metrics, and an operator dashboard. Redis is used for shared application state, with an in-process NumPy vector index as the default semantic-search backend and an optional RediSearch/HNSW backend for shared vector retrieval.

The cache has two distinct operating modes. The default \texttt{exact} mode reuses only an identical UTF-8 prompt within its tenant and cache namespace. The optional \texttt{semantic} mode embeds a query with the pinned \texttt{all-MiniLM-L6-v2} model, searches for a nearby candidate, and applies an adaptive threshold and a Tier-1 structural verifier before reusing an answer. An optional bidirectional NLI cross-encoder can add a further statistical filter. A keyword-based volatility detector bypasses queries that match configured time-sensitive terms. The distinction matters: semantic-mode benchmark results do not describe the default exact-mode request path.

On the repository's 30-pair curated semantic benchmark, the adaptive-plus-Tier-1 policy accepted 5 of 15 positive pairs and 0 of 15 negative pairs. The fixed-threshold baseline accepted 6 positive pairs and 7 negative pairs. These observations demonstrate the intended trade-off on the selected examples, but they do not establish universal correctness or production accuracy. The benchmark is small and hand-curated; larger public datasets, domain-specific negative examples, and real anonymised query distributions are needed before making broader claims.

The cost-aware cascade is implemented as an optional heuristic router. In the checked-in 40-query routing experiment, the default threshold escalates 50\% of requests. Under an illustrative 15:1 strong-to-cheap cost ratio, this corresponds to a simulated 46.7\% cost reduction while retaining all labelled hard queries on the strong tier. This is not a measurement of live provider spending or generated-answer quality. It is evidence that the current heuristic separates the selected easy and hard examples; a learned router and live quality/cost evaluation remain future work.

\section{Limitations}
\begin{enumerate}
    \item \textbf{Small curated datasets.} The cache benchmark contains only 15 positive and 15 negative pairs; the cascade benchmark contains 20 easy and 20 hard prompts. The measured rates are sensitive to these examples and cannot be generalised to arbitrary user traffic.
    \item \textbf{Semantic matching is probabilistic.} Exact matching is the default because embedding similarity and the structural verifier cannot prove that two prompts require the same answer. Tier-1 uses number, negation, and capitalization-derived entity checks rather than a trained NER model. Tier-2 NLI is also statistical and can reject valid paraphrases or accept invalid ones.
    \item \textbf{Heuristic decision rules.} The adaptive threshold, volatility detector, and query-complexity score use hand-written features and rules. They are interpretable but have limited coverage and have not been validated across broad domains.
    \item \textbf{Operational validation is revision-specific.} The latest audit records 50 passing tests and 4 live-Redis tests skipped locally. A release requires fresh green CI, Redis Stack integration, container validation, and load testing on the exact submitted revision.
    \item \textbf{Budget semantics.} The daily request budget counts admitted cache misses and bypasses per API key and UTC day. It does not enforce monetary, token, retry, or cascade-attempt limits.
    \item \textbf{Deployment requirements.} Production operation still depends on correctly supplied secrets, a real upstream provider, shared Redis with finite memory, TLS termination, appropriate network controls, and provider-side financial limits. A successful local test run alone is not production approval.
\end{enumerate}

\section{Future Work}
\begin{itemize}
    \item Expand cache evaluation using public paraphrase datasets and carefully designed hard negatives, with a held-out split and per-domain calibration.
    \item Improve semantic verification with stronger entity and relation extraction, domain-aware checks, and calibrated NLI thresholds; retain exact mode for workloads where false reuse is unacceptable.
    \item Replace heuristic volatility detection and query-complexity scoring with evaluated classifiers, and measure routing against real provider quality and token-cost observations.
    \item Run Redis Stack integration and independent-worker tests on every release candidate; benchmark RediSearch/HNSW at realistic tenant counts and cache sizes.
    \item Conduct load, concurrency, cancellation, failure-recovery, and long-duration tests to establish service-level objectives rather than extrapolating from microbenchmarks.
    \item Complete deployment hardening and operational runbooks, including TLS, secret management, provider-side spend limits, monitoring, backup/restore, and incident response.
\end{itemize}

\section{Final Statement}
VeriGate should be presented as a working, configurable LLM gateway with a research-oriented semantic-cache mode, not as a universally correct or already production-certified caching system. Its strongest defensible contribution is the explicit separation of candidate similarity from answer-reuse verification, supported by a reproducible but deliberately limited benchmark. The report's claims and figures should be refreshed whenever the implementation or evaluation data changes.
