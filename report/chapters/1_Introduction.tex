\section{Background and Motivation}
Internal developer tools, technical support systems, and organizational applications often receive repeated technical questions. An authorized employee may ask how to inspect a deployment; another employee in the same workspace may ask the same task in different words. Reusing a stored response can avoid a provider call. Yet a nearby question can request a different action, environment, permission, or software version. The nearest question is therefore only a \emph{candidate} for reuse; its recorded answer must also fit the new task.

VeriGate is an organization-aware LLM gateway for applications that explicitly integrate with its supported HTTP API. It is not a chatbot. A normal ChatGPT website or Codex session does not automatically pass through this gateway, and a user's subscription credential is not extracted for provider access. An application sends a VeriGate credential; the server resolves its provider profile and owns the upstream provider credential.

\section{Intended Users and Organizational Use}
The intended installation is one gateway service that can serve several organizations while keeping their data separate. Within an organization, an administrator configures trusted applications, employee identities, workspace membership, and provider profiles. Employees use their existing integrated application; they need not visit a gateway administration screen or choose a storage scope for every question. When the request omits a scope override, the server resolves an authorized default and may restrict storage further based on the request and response.

Consider an engineering workspace in Organization A. One employee asks how to inspect a deployment and receives a reusable procedure. A colleague later asks for the same procedure in different words. If the stored answer satisfies the colleague's task and the sharing rules permit access, the gateway can reuse it. A private account-specific response must not enter that shared pool. An employee in Organization B cannot retrieve Organization A's entry even when the question is identical. Organization B builds its own eligible cache. Thus the intended savings arise from repeated work across authorized users, not from asking one user to repeat a question many times.

This model is suitable for internal developer portals and technical support applications with recurring procedures. Requests requiring fresh observations, private account state, or unsupported conversation history need different handling. Multi-organization isolation is an implemented configuration boundary; operating at thousands of organizations remains a capacity-validation goal.

\section{Problem Definition}
The gateway must distinguish four operations. An \emph{exact repeat} can use a scope-local stored response after a current-entry check. \emph{Semantic retrieval} embeds a new request and returns nearby stored questions from an authorized scope; similarity only ranks candidates. \emph{Answer-aware assessment} compares the incoming question with a stored question \emph{and its particular answer}, using structural checks and an optional model signal. If no candidate is approved, \emph{provider fallback} generates a new response. A candidate rejected or marked VERIFY has not thereby been proved false; it is simply not served from cache.

The engineering problem includes access control as well as quality. Employees A and C may share eligible technical answers in a workspace when both are authorized. Private answers remain restricted to the subject and application scope. A content classifier can conservatively narrow a shared write, but it cannot establish that all sensitive content has been detected.

\section{Objectives and Scope}
The implemented prototype provides credential resolution, organization and provider-profile configuration, exact or semantic cache modes, scoped Redis storage, a local MiniLM embedding option, RedisSearch top-$k$ retrieval, optional answer-aware candidate assessment, provider routing, JSON and streaming responses, admission controls, and operational metrics. Exact mode is the general default. The historical adaptive threshold and query-only verifier are alternative baseline paths when the answer-policy artifact is absent; they do not run simultaneously with the answer-aware policy.

The evaluation asks whether specific requests follow the intended scope and decision path and how much suitable reuse the opt-in policy achieves on controlled examples. It does not establish factual correctness of arbitrary upstream answers, production monetary savings, a universal latency target, or company-scale capacity. The contribution is the integration of scope-aware storage with candidate-level answer suitability checks and a traceable evaluation of their trade-offs, including negative results. Related caches already support semantic search, adaptive boundaries, and verification (Chapter~2).

\section{Cost and Latency Objectives}
The economic motivation is to avoid generating the same useful answer repeatedly. On a cache hit, VeriGate avoids the upstream generation call. It still pays for its own CPU, memory, Redis operations, and any verification. On a miss, those checks can add work before generation. Cost effectiveness therefore depends on how often eligible requests recur, how reliably suitable answers are accepted, and the relative cost of verification and generation. Chapter~6 gives a break-even model alongside measured results rather than assuming that every cache hit is free.
